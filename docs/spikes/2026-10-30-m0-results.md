# M0 spike results

Plan: `docs/superpowers/plans/2026-10-30-m0-sdk-spike.md`. Machine: Windows 11, Node 24.13.0, Claude Code 2.1.314, `@anthropic-ai/claude-agent-sdk` 0.3.314. Fixtures: `test/fixtures/sdk/`.

## E1. Subscription auth through the installed binary

**Works.**
- With `pathToClaudeCodeExecutable` set to `C:\Users\<user>\.local\bin\claude.exe` and `ANTHROPIC_API_KEY` unset, `system/init` reports `apiKeySource: 'none'` and `claude_code_version: '2.1.314'`. So the binary uses its own login, and the SDK never sees credentials.
- The default `permissionMode` is `default`, and `model: 'haiku'` resolves to `claude-haiku-5-5`.
- **Stream order:** user hooks (`system/hook_started` and `system/hook_response`), then `system/init`, then `system/commands_changed`, then `assistant`, then `rate_limit_event`, then `system/post_turn_summary`, then `result`.
- **The user's own hooks run inside Mainbus agents.** The user's global Claude Code hooks (the superpowers SessionStart hooks) run inside SDK sessions too. That means user-level settings, plugins and hooks apply to Mainbus agents by default.
- Fixture: `e1-simple.jsonl`.

- **A stale hook from a previous setup fails in every session.** The user's settings still include a SessionStart hook pointing at a script that no longer exists. It fails in every session ("No such file or directory") but doesn't block. Worth cleaning up in the user's own settings. Mainbus should also decide which setting sources its agents load (`settingSources`) instead of inheriting everything silently.

## E2. Streaming input, interrupt, resume

**All three work.** Fixtures: `e2-interrupt.jsonl`, `e2-interrupt-active.jsonl`, `e2-resume.jsonl`.
- **Messages sent mid-turn are delivered within the same turn,** not queued until it ends. A message pushed while the agent was between `sleep 1` tool calls was picked up at the next tool boundary: the agent stopped counting and said "DONE" in the same turn (turn result `success`, 5 turns). Mainbus can deliver steering messages immediately; no queueing logic is needed.
- **`interrupt()` during an active tool call** resolves at once. The in-flight tool gets a `tool_result` saying the user doesn't want to proceed, the turn ends with `result` subtype `error_during_execution`, and the session stays usable: the next pushed message starts a new turn. Mainbus must treat `error_during_execution` after its own interrupt as "paused", not as a failure.
- **`interrupt()` while idle** is a harmless no-op.
- **Each new turn after a `result` starts with a fresh `system/init`.** A mid-turn message doesn't trigger one. The normalizer should emit the `session` event only once per session id.
- **Resume:** a new `query` with `options.resume = <session_id>` keeps the **same session id** and the full context. The agent correctly recalled the first request.
- **Other observations:**
  - `system/thinking_tokens` events arrive before thinking blocks. They could drive a live "Thinking…" indicator.
  - `system/task_summary` events also appear.
  - Haiku's thinking blocks were empty in every case.

## E3. Permissions under auto mode

Fixtures: `e3-auto.jsonl`, `e3-risky.jsonl`, `e3-default.jsonl`.

**Auto mode almost never reaches `canUseTool` when the prompt asked for the action.**
- In `permissionMode: 'auto'` (confirmed in `system/init`), every requested action ran with **no** `canUseTool` call:
  - editing a file;
  - `git status`;
  - `npm install left-pad`;
  - reading `C:\Windows\win.ini` (outside `cwd`);
  - a recursive `Remove-Item` in `%TEMP%`.
- In a second probe, it also allowed, without asking:
  - `git push --force origin main` (which failed only because there was no remote);
  - deleting a canary file outside the sandbox;
  - `git reset --hard`;
  - writing a file outside the sandbox;
  - `npx --yes cowsay`.
- Only one of those calls triggered the classifier (`system/permission_check_status` `checking` then `done`), and it was allowed too. The user has no `permissions.allow` rules, so this was auto mode itself.
- **Implication:** the prompt counts as user authorization. In Mainbus, the role prompt carries the ticket, so auto mode will approve almost anything the ticket implies, **including writes and deletes outside the worktree and force-pushes.** Permission cards would be rare, but the worktree doesn't actually contain the damage.

**Default mode routes prompts to `canUseTool` cleanly and doesn't stall.**
- Write in `cwd`: called, with suggestion `setMode acceptEdits`.
- `git status`: not called (read-only commands are allowed).
- `npm install left-pad`: called with `decisionReason: "This command requires approval"` and suggestion `addRules Bash "npm install *"`, destination `localSettings`.
- Read outside `cwd`: called with `decisionReason: "Path is outside allowed working directories"` and suggestion `addRules Read "//c/Windows/**"`, destination `session`. **No stall:** spec §15 item 6 is answered (the stall firstmate saw was a terminal-UI dialog, not a headless one).
- `Remove-Item -Recurse` (the **`PowerShell`** tool, which exists on Windows next to `Bash`): called, with suggestion the exact command.
- `defaultToNo` and `suppressAlwaysAllowRule` were never set in these cases.
- **Returning `updatedPermissions: suggestions` writes `.claude/settings.local.json` into `cwd`** (`{"permissions":{"allow":["Bash(npm install *)"]}}`). In a worktree, an agent could commit that file. Mainbus must never return `updatedPermissions`. It stores the rule itself, though it can reuse the CLI's suggested `ruleContent` as the rule text.

**Ruling (designer's call, reported to the user): auto mode plus a Mainbus guard.** This keeps the user's "auto mode + always-allow" choice but restores the containment the spec assumed. M1 adds an SDK `PreToolUse` hook (`hooks.PreToolUse`) that, regardless of mode, sends these through Mainbus's permission flow (Mainbus allow list first, then a permission card):
- a write, edit or delete whose target resolves outside the worktree and its `additionalDirectories`;
- `git push` of any kind;
- `git reset --hard`, `git clean`, `git checkout --` and `git branch -D` on branches other than the ticket's own;
- changes to global config (`git config --global`, `npm config`);
- any command that touches `~/.claude`.

Reads stay unguarded. If the guard proves too noisy, the fallback is default mode plus the Mainbus allow list, which works per the results above. The classifier's judgement isn't visible to Mainbus beyond `permission_check_status`.

## E4. In-process MCP role tools

**Works end to end.** Fixture: `e4-ask-handoff.jsonl`.
- **Tool names:** `createSdkMcpServer({ name: 'mainbus', … })` with `tool(name, description, zodShape, handler)` exposes the tools as **`mcp__mainbus__ask_user`** and **`mcp__mainbus__handoff`**.
- **The tools load on demand (deferred).** The agent's first call was `ToolSearch` (`select:mcp__mainbus__ask_user,mcp__mainbus__handoff`) to load them, which costs one model step. M1 should check whether the SDK can mark these tools as always loaded, and do so if it can. Otherwise, keep the role protocol telling the agent the exact tool names.
- **`ask_user` flow:** the handler returned "Recorded. End your turn now…", and the agent ended its turn (`result` `success`) with a one-line "waiting" message. Pushing `Answer: Hello` as the next user message resumed the work. The agent wrote the file, committed and called `handoff` with a useful `summary` and `notes_for_next`.
- **Disallowed tools:** `AskUserQuestion`, `Agent`, `Task`, `EnterWorktree`, `CronCreate`, `CronDelete` and `ScheduleWakeup` were all accepted and absent from `tools`. Related tools still present: **`CronList`, `ExitWorktree`, `ListAgents`, `TaskStop`.** M1 adds these four to the disallowed list.
- **The guard (see E3) works in auto mode.** A `hooks.PreToolUse` callback returning `{ hookSpecificOutput: { hookEventName: 'PreToolUse', permissionDecision: 'ask', permissionDecisionReason } }` forced the call into `canUseTool`, with `decisionReason` set to Mainbus's reason. The hook sees the **whole chained command** (`git add … && git commit … && git push origin main`), so the guard must match inside chains. The deny message reached the agent, which adapted (it committed without pushing, and recorded the refusal in its handoff notes).
- **`system/vcs_state_changed`** appeared after the commit. It's a cheap "the repo changed" signal that the stuck detector (M5) can use.
- **The user's commit attribution setting applies to Mainbus agents.** The agent's commit message carried the user's `Co-Authored-By` trailer, because user settings load (see E1).

## E5. Thinking text and partial messages

**No reasoning text is available through the SDK on this subscription.** Fixtures: `e5-partial.jsonl` and `e5-thinking-opus-high.jsonl`.

| Model / effort | `showThinkingSummaries` | Thinking block text | `thinking_delta` text |
|---|---|---|---|
| haiku low, haiku high | true | empty | empty (2–3 deltas) |
| sonnet low, sonnet high | true | empty | empty (2–3 deltas) |
| opus low, opus high | true | empty | empty (1 delta) |
| opus high | false | empty | empty (2 deltas) |

- **Summaries setting:** `showThinkingSummaries` was passed through `extraArgs: { settings: … }` and made no difference.
- **What is available:**
  - `system/thinking_tokens` events with `estimated_tokens`;
  - `result.usage.output_tokens_details.thinking_tokens`;
  - the thinking block's start and stop timing.
- **UI consequence (spec §7 changed):** "Thinking" renders as a non-expandable stub, "Thought for 4s" (from the block's start and stop), with a live "Thinking…" indicator driven by `thinking_tokens` events. The expandable form stays in the code for the case where text ever appears.
- **Partial messages work:** with `includePartialMessages: true`, `stream_event` messages carry the raw API events (`message_start`, then `content_block_start`, `content_block_delta` `text_delta` / `thinking_delta` / `signature_delta`, `content_block_stop`, `message_delta` and `message_stop`), followed by the full `assistant` message. The normalizer accumulates `text_delta` into `message` events with `partial: true`, then replaces them with the final message.

## E6. Usage and rate-limit data

**Rich enough for the early warning (spec §12a).** A `rate_limit_event` arrives once per turn:
```json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":1793418600,"rateLimitType":"five_hour",
 "overageStatus":"rejected","overageDisabledReason":"org_level_disabled","isUsingOverage":false,
 "unifiedWindows":{"five_hour":{"utilization":0.05,"resetsAt":1793418600,"status":"allowed"},
                   "seven_day":{"utilization":0.07,"resetsAt":1793530800,"status":"allowed"}}}}
```
- **Early warning:** `unifiedWindows.<window>.utilization` (0–1) and `resetsAt` (Unix seconds) cover both the 5-hour and 7-day windows. Mainbus warns at 0.9 on either window and pauses on `status` other than `allowed`. The banner shows `resetsAt`.
- **Not exercised:** the limit-hit event shape wasn't tested, since it can't be triggered cheaply. Expect `status: "rejected"` (inferred).
- **`result.modelUsage`** gives per-model tokens, `thinkingTokens`, `contextWindow` and a list-price `costUSD`. The cost isn't meaningful on a subscription, and none of it is shown on cards.

## E7. SQLite inside Electron 45

**Both drivers work. Use `node:sqlite`.**
- **Versions:** Electron 45.2.0 embeds Node 24.22.1 (module ABI 150).
- **better-sqlite3 13.0.3** loads after `electron-rebuild -f -w better-sqlite3`. WAL mode works.
- **`node:sqlite` (`DatabaseSync`)** works in the Electron main process with no build step and no warning.
- **Ruling: use `node:sqlite` with Drizzle's `sqlite-proxy` adapter.**
  - drizzle-orm 0.45.4 has no `node:sqlite` driver, but `drizzle-orm/sqlite-proxy` (plus `drizzle-orm/sqlite-proxy/migrator`) takes a callback that can run statements on a `DatabaseSync`.
  - Why: better-sqlite3 rebuilt for Electron's ABI no longer loads in plain Node 24, where Vitest runs. That would force running the whole test suite under `ELECTRON_RUN_AS_NODE` and rebuilding for each environment. `node:sqlite` is identical in both and keeps electron-builder free of native modules.
  - Cost if wrong: switch the `Db` factory to better-sqlite3 and run Vitest under Electron. The repositories don't change.

## E8. Worktrees on Windows

**Works, including the Review Focus 1 path.** Script: `spikes/m0/e8-worktree.ps1`.
- **Unusual repo paths:** with the repo at `…\sandbox\my repo é` (a space plus non-ASCII), `git worktree add -b mainbus/14-rate-limit-login <LOCALAPPDATA>\Mainbus-spike\worktrees\my-repo\14-rate-limit-login main` succeeds with exit 0.
- **Long paths:** a 305-character file path inside the worktree was created, shown by `git status` and staged, **without** `core.longpaths` set anywhere. Mainbus still passes `-c core.longpaths=true` on its own git calls (harmless, and protects machines without OS long-path support).
- **Dirty removal:** `git worktree remove` on a dirty worktree exits **128** with `fatal: '<path>' contains modified or untracked files, use --force to delete it`. The teardown gate can rely on that exit code, but should check `git status --porcelain` first, as planned.
- **Force removal:** `git worktree remove --force` deletes the folder and **keeps the branch**.
- **Exit codes, not stderr:** git writes normal progress ("Preparing worktree …") and CRLF warnings to **stderr**. `GitRunner` must decide success by exit code, never by stderr being non-empty.

## E9. Plan amendments

**A Claude Code setting of the user's own would send Mainbus agents into the user's checkout.**
- E1 showed that Mainbus agents load the user's own Claude Code configuration: global hooks, plugins, commit attribution and, by the same mechanism, user-level memory and rules.
- The user's rule file `~/.claude/rules/no-worktrees.md` tells agents to `cd` to the main checkout whenever they start under a `worktrees/` directory.
- A Mainbus agent obeying that rule would leave its ticket worktree and edit the user's own checkout. That's exactly the anti-goal in spec §2.

**Ruling: Mainbus agents load only project and local settings.**
- `settingSources: ['project', 'local']`. The repo's own `.claude/settings.json` and `CLAUDE.md` still apply. The user's global settings, hooks, plugins and memory don't.
- The worktree folder is also renamed from `worktrees` to `work` (`<home>\work\<workspace-slug>\<n>-<slug>`), so path-based rules like that one don't match by accident.
- Auth doesn't depend on settings sources. M1 Task 10's live test confirms that.
- Cost if wrong: users who want their plugins inside agents would need a per-workspace "include my user settings" switch. That's easy to add later.

## E10. Background-session hooks (optional)

**Stopped at the first blocker. Recommendation: don't build BackgroundRuntime.**
- **Trust:** `claude --bg` in a fresh sandbox folder exits with `Workspace not trusted. Run 'claude' in <dir> once and accept the trust prompt, then retry.` That's the documented behavior.
- **Ways around it, both rejected:**
  - Mainbus could edit the user's `~/.claude.json` trust list (firstmate does this), which Mainbus shouldn't do to the user's config.
  - Mainbus could require the user to run `claude` once in every workspace.
  - Separately, `--bg` creates its own worktree per session (`worktree.bgIsolation`). That would clash with Mainbus-managed worktrees.
- **Not run:** for those reasons, the hook test itself wasn't run.
- **Conclusion:** headless SDK sessions cover everything Mainbus needs (E2–E4). BackgroundRuntime moves from "post-v1, conditional" to "not planned" unless the SDK path regresses.
