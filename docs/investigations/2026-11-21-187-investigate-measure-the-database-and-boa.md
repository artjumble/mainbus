# Investigation: database size, board speed, event compaction and export

## The question

#180 recommended an archive state and left one optional step: measure the database and the board as tickets pile up. Then decide (1) whether to compact the events of old archived tickets and (2) whether to offer "Export archive to files". The spec asks for database size by table and per ticket, `boardView` refresh time at about 150, 1,000 and 5,000 tickets with and without archiving, an estimate of what compaction would save, and a recommendation on export.

## What I did

All work was on copies, in the ticket's scratch folder. The real data home was only read, to copy it once.

- **Database size.** I copied the real `mainbus.db` (taken 2026-11-21: 216 tickets in 4 workspaces, 187 Done, about 3 weeks of history) and measured it with `dbstat` and SQL. Event kinds were read from the `json` column.
- **Board speed.** Test code in the scratch folder, not the repo, opened the copied database with the real `openDb`, `createRepos` and `TicketRunner.boardView`. It repeated the body of `boardView` in `src/engine/index.ts` (the real function is a closure that can't be called alone). Only the freshness lookup and run-setting notices were left out; there are no open runs in the copies. The larger databases were generated by cloning the real Done tickets, with their runs, events and criteria, into 1,000 and 5,000 tickets. All sit in one workspace, which is the worst case. "With archiving" means all Done tickets are archived except the original ones done in the last 14 days (128 left on the board: 29 open, 99 Done). Each figure is the median of 7 refreshes after a warm-up, on a Windows machine with Node's built-in `node:sqlite`.
- **Compaction.** I applied candidate compaction rules to a copy of the real database. Then I recomputed `ticketTimeFor` (the Time report) and `ticketUsage` for every ticket with the real code, and compared the results before and after.
- **Not measured.** I did not measure the Electron IPC transfer, React rendering or the orchestrator's `list_tickets` (not archive-aware yet; #183 only did the engine). JSON size is reported as a proxy for the transfer cost.

## Findings

### 1. Database size

The file is 52.0 MB (12,715 pages of 4 KB, no free pages).

| Table | MB | Share |
|---|---|---|
| `agent_events` | 42.2 | 81% |
| its primary-key index | 3.6 | 7% |
| `orchestrator_events` | 2.0 | 4% |
| `tickets` | 1.5 | 3% |
| `decisions` | 0.7 | |
| `ticket_runs` | 0.6 | |
| `proposals`, `agent_runs`, `criteria`, other | under 0.3 each | |

Rows: 63,840 events, 553 agent runs, 216 tickets. `agent_events` plus its index is **88% of the file**.

**Per ticket** (193 tickets have events; the event JSON totals 33.1 MB, which takes 42.2 MB on disk):

| | Event JSON per ticket |
|---|---|
| Mean | 171 KB |
| Median | 142 KB |
| 90th percentile | 338 KB |
| Maximum | 642 KB (1,042 events) |

On disk that is about 220 KB per ticket for events, plus about 7 KB for the `tickets` row (spec, intent, report) and about 20 KB for its handoffs and messages inside the events. The whole file averages 241 KB per ticket. The database grew about 2.5 MB per day over these three weeks (216 tickets, about 10 a day across all workspaces, about 8 a day in the busiest). That is about 0.9 GB a year, or about 3,600 tickets a year.

**What the event bytes are** (kind, rows, MB of JSON):

| Kind | Rows | MB | Note |
|---|---|---|---|
| `tool_call` | 19,766 | 17.3 | Bash 7.1, Write 3.6, Edit 2.8, `handoff` 2.3 (a copy of the handoff event), `submit_report` 0.2 (a copy of the report) |

**Backups are as large as the problem.** `openDb` copies the whole database (`VACUUM INTO`) into `backups\` before every migration that is pending, and nothing ever deletes them. The data home already holds 39 backups totalling 701 MB, more than the live database. Every byte kept in `agent_events` is copied into every future backup.

### 2. Board refresh time

Time for one `boardView` of one workspace (the work listed in `index.ts:979`):

| Tickets built | Without the fix | With an index on `agent_runs.ticket_run_id` |
|---|---|---|
| 216 (the real database, no archive) | 105–111 ms | 110–119 ms |
| 216 with 88 archived (128 built) | 59–65 ms | 60–67 ms |
| 1,000, no archiving | 590–750 ms | 550–590 ms |
| 1,000 with archiving (128 built) | 125–134 ms | 73–85 ms |
| 5,000, no archiving | **20.5–23.8 s** | 3.4–3.7 s |
| 5,000 with archiving (128 built) | **330–340 ms** | 93–96 ms |

The "with archiving" rows are with `archived left out`; building every ticket regardless (what `includeArchived` does) costs the same as without archiving.

What the numbers say:

- **Archiving is what keeps the board flat.** With the 128 tickets of the window, the refresh time is 60–95 ms at every database size (once the index below exists). Without it the cost grows with the ticket count.
- **There is a hidden quadratic cost, separate from archiving.** `runs.listForTicketRun` (`src/engine/store/runs.ts:350`) filters `agent_runs` by `ticket_run_id`, and that column has no index (`EXPLAIN QUERY PLAN` says `SCAN agent_runs`). `boardView` runs it once per ticket, so the cost is tickets times total runs. On the 5,000-ticket database it took 2.28 ms per call, against 0.016 ms with `CREATE INDEX agent_runs_ticket_run_idx ON agent_runs(ticket_run_id)`. That index alone takes the 5,000-ticket board from about 22 s to about 3.5 s, and the archived 5,000-ticket board from 340 ms to 95 ms. It would help even with archiving off, and also helps the Done strip and anything else that lists a ticket run's runs.
- **Where the rest goes, at 5,000 tickets with the index:** `tickets.list` 1.15 s (it loads every row with its spec and report, and loads criteria with a 5,000-id `IN` list), and the per-ticket runner step 2.4 s.
- **The workspace-wide lookups ignore archiving.** `attachments.listForWorkspace`, `ticketEdits.listForWorkspace`, `dependencies.forWorkspace` and `notesForWorkspace` still read every ticket's rows when the board leaves archived tickets out. They cost about 30 ms in total at 5,000 tickets (about 1 ms at 216), and `attached.filter(...)` runs once per ticket against the full list. This is small, but it is the part that would grow with history after the index fix.
- **The board payload is large.** The refresh returns each ticket's whole row. That is 1.6 MB of JSON for 216 tickets (about 7.5 KB each, mostly `spec` and `report`, and a report can reach 50 KB), 7.7 MB for 1,000 and 38 MB for 5,000. With archiving the window is 0.97 MB at every size. I did not measure the transfer and render cost, so this is a lead, not a measured problem.
- **When the board gets slow.** The busiest workspace gets about 8 tickets a day. Without archiving it would be at 1,000 tickets in about 4 months (about 0.6 s per refresh) and at 5,000 in about 1.6 years (about 22 s now, about 3.5 s with the index).

### 3. Event compaction

**What the Time report and usage depend on.** More than the four kinds in the spec. `runBreakdown` (`src/shared/timeBreakdown.ts`) takes turn starts from `session`, `user_message`, `nudge`, `redirected`, `resumed`, `message`, `thinking`, `tool_call`, `tool_result`, `needs_input` and `error`. It takes turn ends from `usage`, `turn_end`, `stopped` and `process_exit`. It also reads `paused`, `queued`, `setup` and the text of `notice` (to find usage-limit pauses). For shell tools it reads the command text, to classify the time. `ticketUsage` reads `usage`. So **rows must stay**, in order, with their timestamps; only the weight of their payloads can be shrunk.

**Rule set A (no rows deleted), tested on the real data:**

- `tool_call`: keep `id` and `name`; for shell tools keep the whole `command`; for the handoff and submit-report tools keep no input (it duplicates the handoff event and `tickets.report`); for others keep the first 200 characters of the main field.
- `tool_result`: keep `id` and `ok`; cut `summary` to 80 characters.
- `notice`: keep the text in full when it is a usage-limit pause notice; otherwise cut it to 160 characters.
- `report`: drop the text (`tickets.report` has it).
- Everything else, including `handoff`, `message`, `usage`, `turn_end`, decisions and criteria events, is untouched.

**Result:** event JSON 33.1 → 18.4 MB; file 52.1 → 34.5 MB after `VACUUM` (−34%). The Time report and usage totals were **identical for all 216 tickets**. By kind: `tool_call` 16.9 → 8.4 MB, `notice` 5.1 → 1.0, `tool_result` 5.0 → 3.1, `report` 0.22 → 0.

**Rule set B (A, plus deleting `thinking` and `rate_limit` rows):** 52.1 → 32.3 MB, but the report changed for one ticket. Those kinds are turn starts and limit ends, so deleting rows is not safe. **Don't delete rows.**

**What compaction costs the user.** The thread of a compacted ticket shows shortened tool inputs and results (the agent's messages, handoffs and decisions stay in full). Compaction is one-way: the cut text is gone, and the backups hold the old copies only until they are pruned.

**What it would save and when.** Today, nothing: the oldest ticket is 3 weeks old, so no ticket has been Done for "N months". Compaction saves about a third of the events, which is about 0.3 GB a year at the current pace (about 0.9 GB a year before). It does nothing for board speed: Done tickets never read their events on the board path (`inspect` skips them), and the per-ticket time was the same with or without events.

### 4. Archive export

An export would write a markdown or JSON file per ticket. A ticket without its tool log is about 30 KB (its row, handoffs, messages and decisions); with the full log it is about 240 KB. Archiving never deletes anything (#183 keeps the rows), so an export is not needed to keep access: the Archive view and `get_ticket` already open the ticket. Its remaining uses are portability and disaster recovery, and the migration backups and a data-home copy already cover recovery.

## Recommendation

1. **Don't build event compaction now.** It saves about a third of the disk at best, doesn't help speed, can't touch anything yet, and its saving (about 0.3 GB a year) is smaller than the backups' (701 MB already). Revisit when the data home passes about 1 GB or when archived tickets are over 6 months old. The tested rules above are the starting design (rule set A, no row deletion, a per-workspace setting, a notice, and the Time report and usage totals checked equal in a test). The change should go in a separate ticket then.
2. **Don't build the export now.** Nothing is deleted, so there is nothing to protect. If it is wanted later, a single "Export ticket as JSON/markdown" action on an open ticket would be the small first step. A bulk "export the archive" has no user need yet.
3. **Do the cheap changes the measurements found, in this order:**
   - add the missing index (about 6× faster board at 5,000 tickets with archiving off, about 3.5× faster with it on);
   - prune the migration backups;
   - make the workspace-wide lookups archive-aware;
   - stop writing the duplicated text.

   They are independent of the archive tickets (#183 onwards) and can ship before or after them.

## Proposed change tickets

**A. Index `agent_runs.ticket_run_id`** (Change; small; do first)
- Scope: a migration with `CREATE INDEX agent_runs_ticket_run_idx ON agent_runs(ticket_run_id)` and the matching schema entry.
- Criteria: `listForTicketRun`'s query plan uses the index (a test checks it); the migration test passes; a measured `boardView` on a generated 1,000-ticket copy is no slower and the 5,000-ticket figure drops from about 22 s to under 5 s.

**B. Prune old database backups** (Change; small)
- Scope: after a successful migration, keep the newest N backups (suggest 5) and anything under N days old (suggest 14), and delete the rest. Never delete the backup just taken. Report what was removed.
- Criteria: tested with a temporary `MAINBUS_HOME` and a fake clock; a failed migration keeps all backups; the backup folder doesn't grow without bound across repeated upgrades.

**C. Archive-aware lookups and a slimmer board payload** (Change; medium; depends on #183)
- Scope: make `attachments.listForWorkspace`, `ticketEdits.listForWorkspace`, `dependencies.forWorkspace` and `notesForWorkspace` skip archived tickets for the board (the Archive view and `get_ticket` load by ticket id); build the per-ticket maps once instead of filtering per ticket; consider leaving `report` and `spec` out of the board's refresh for Done tickets and loading them when a ticket opens. Measure the transfer and render time before choosing the last part.
- Criteria: with 5,000 tickets and archiving, the board refresh stays within 20% of the 128-ticket figure; blocker chips and "promoted from" links still open archived tickets; the Time report and usage totals are unchanged.

**D. Stop writing the same text twice** (Change; small; optional)
- Scope: don't store the unattended notice's command (it is in the tool call) and don't store the `handoff` and `submit_report` tool inputs (they are in the handoff event and `tickets.report`). That would cut about 6.5 MB of the 33 MB (about 20%) from new tickets with no change for the user, if the thread view shows those tool rows from the event. Check how the thread renders them first.
- Criteria: the Time report and usage totals unchanged for a fixture run; the thread view of a new ticket looks the same; tested.

**Not proposed now:** event compaction (rule set A) and archive export. Both can be filed later with the triggers above.

## Limits of this report

- One real database from one user, 3 weeks old, so there is no data on tickets that have been Done for months. The larger databases are clones of its Done tickets, so they repeat its event mix.
- Speed was measured with Node's built-in SQLite, warm caches and one workspace holding everything; the app's IPC, React rendering and `FreshnessStatus` are not included. Absolute times will differ on other machines; the growth is the useful part.
- `list_tickets` was not measured (it isn't archive-aware yet).
- Compaction was checked for the Time report and usage only. Other readers of old events (the thread view, `get_recent_events`, the stuck detector's history, done-review) would show the shortened text and were not tested.
- No code, schema or user data was changed; scratch files (including the database copies) were deleted afterwards.
