# M0 Agent SDK Spike Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This is a spike: no TDD, no production code. Each experiment ends with a written finding.

**Goal:** Prove or disprove every assumption in spec §15 on this Windows machine, before any MVP code is written.

**Architecture:** One throwaway Node + TypeScript script per experiment under `spikes/m0/`, run with `npx tsx`. Two outputs are kept:
- recorded SDK message streams in `test/fixtures/sdk/`, which M1's normalizer tests replay;
- the results doc.

**Tech Stack:** Node 24, TypeScript, `@anthropic-ai/claude-agent-sdk` 0.3.314, `tsx`, the installed `claude.exe` (Claude Code 2.1.314), and Electron 45 for E7 only.

**Spec:** `docs/superpowers/specs/2026-10-30-mainbus-design.md`

## Global Constraints

- Drive only the installed official `claude.exe`. Find it with `where.exe claude` and pass it as `pathToClaudeCodeExecutable`.
- Never read, copy or print anything from `~/.claude/.credentials.json` or other credential stores.
- `ANTHROPIC_API_KEY` must be unset in every experiment's environment. Each script asserts this at start and exits if it's set.
- Every experiment runs in a scratch git repo under `spikes/m0/sandbox/` (gitignored), never in the mainbus checkout itself.
- Use the cheapest model that answers the question (`haiku` or `sonnet` at low effort). Only E5 needs larger models.

## Review Focus

Not applicable: spike code is thrown away. Findings feed M1's Review Focus.

### Task 2: Streaming input, interrupt, resume (E2)

**Files:** Create `spikes/m0/e2-session.ts`.

- [ ] **Step 1:** Write the script.
  - Streaming input: use an async-iterable input queue, pushing `SDKUserMessage`s. Start with "Count slowly from 1 to 30, one number per line, using Bash `sleep 1` between numbers." Push a second message, "Stop and say DONE", 5 s later.
  - Interrupt: call `q.interrupt()` 10 s after start, then push "Say RESUMED".
  - Resume: end the input, capture `session_id` from `system/init`, then start a new `query` with `options.resume = session_id` and the prompt "What was the last thing I asked you?"
- [ ] **Step 2:** Run the script. Note four things:
  - whether the mid-turn message was queued or interrupted the turn;
  - what `interrupt()` emits, and whether the session continues;
  - whether resume restores context;
  - whether the resumed `session_id` is the same.
- [ ] **Step 3:** Record `test/fixtures/sdk/e2-interrupt.jsonl` and `e2-resume.jsonl`.
- [ ] **Step 4:** Write the E2 finding, then commit.

### Task 3: Permissions under auto mode (E3)

**Files:** Create `spikes/m0/e3-permissions.ts`.

- [ ] **Step 1:** Write the script with `permissionMode: "auto"`, `cwd` set to a sandbox, and a `canUseTool` that logs `toolName`, `input`, `decisionReason`, `suggestions`, `defaultToNo` and `suppressAlwaysAllowRule`, then returns allow.
  - Prompt it to:
    1. edit a file in the sandbox;
    2. run `git status`;
    3. run `npm install left-pad`;
    4. read `C:\Windows\win.ini`, which is outside `cwd`;
    5. run `Remove-Item -Recurse $env:TEMP\mainbus-spike-x`.
  - Run it twice: once without and once with `additionalDirectories: ["C:\\Windows"]`.
- [ ] **Step 2:** Run both versions. Record:
  - which actions reached `canUseTool`, and which were auto-allowed or auto-denied;
  - whether the outside-`cwd` read stalled or reached the callback (spec §15 item 6).
- [ ] **Step 3:** Try returning `{ behavior: "allow", updatedInput: input, updatedPermissions: suggestions }` for action 3, then rerun. Note where the rule was written. Mainbus must keep its own allow list and **not** write `.claude/settings.local.json` into the user's repo. If suggestions only target local settings, the finding is "Mainbus stores rules itself and checks them before deciding".
- [ ] **Step 4:** If auto mode is unavailable or always denies headless, rerun with `permissionMode: "default"` plus `allowedTools` for edits. Record the fallback behavior (spec §9 "Verify in M0").
- [ ] **Step 5:** Record `test/fixtures/sdk/e3-permission.jsonl`. Write the E3 finding, then commit.

### Task 4: In-process MCP role tools (E4)

**Files:** Create `spikes/m0/e4-mcp.ts`.

- [ ] **Step 1:** Write the script.
  - Define `createSdkMcpServer({ name: "mainbus", version: "0.0.0", tools: [tool("ask_user", …), tool("handoff", …)] })` with zod schemas:
    - `ask_user`: `{ question: string, options: string[], recommended?: number }`. It returns the text `Recorded. End your turn now; the answer will arrive as your next message.`
    - `handoff`: `{ summary: string, notes_for_next: string }`.
  - Pass it via `mcpServers: { mainbus: server }`.
  - Disallow built-in tools with `disallowedTools: ["AskUserQuestion", "Agent", "Task", "EnterWorktree", "CronCreate", "ScheduleWakeup"]`.
  - Append the system prompt `{ type: "preset", preset: "claude_code", append: "<role protocol text from spec §9>" }`.
  - Prompt: "Create hello.txt. Before writing it, ask the user (with ask_user) whether it should say Hi or Hello. After writing it, commit and call handoff."
- [ ] **Step 2:** Run the script. When `ask_user` fires, check whether the turn ends (a `result` arrives). Then push the answer "Hello" as the next user message.
  - Expected: the agent writes the file, commits and calls `handoff`.
- [ ] **Step 3:** Note the MCP tool names as they appear in `tool_use` blocks (expected `mcp__mainbus__ask_user`). Check whether the tools need permission under auto mode, and whether any disallowed tool name is unknown or errors.
- [ ] **Step 4:** Record `test/fixtures/sdk/e4-ask-handoff.jsonl`. Write the E4 finding, then commit.
